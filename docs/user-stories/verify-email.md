# メールアドレスを確認して利用を始められる

> ステータス: 実装済み。

## ストーリー

登録するユーザーとして、自分のメールアドレスに届いたコードを使って登録を完了したい。
自分が受信できるアドレスをアカウントに登録するため。

## 動作確認の手順

[認証メールの開発手順](../development/auth-email.md)で送信方法とデータを準備する。
ローカルでは `AUTH_EMAIL_DELIVERY=console bun run dev:server` で起動すると、コードが開発サーバーのログに `local-auth-email` として出る。

1. ブラウザで http://localhost:3000/app/sign-up を開いて新規登録する。
   - `ichiro <noreply@mail.ichiro.app>` から6桁のコードが届き（ローカルではログに出て）、メール確認画面（`/app/verify-email`）へ進む。
   - コードを確認するまでは、`/app` などを開いてもメール確認画面に戻され、ホームや保護された API を利用できない。
2. 誤ったコードを入力する。
   - 入力欄は数字以外を取り除き、6桁までしか入らない。
   - 誤ったコードではエラーになり、未確認のままになる。
   - 5回間違えると正しいコードでも利用できなくなる。
3. 60秒待ち、「認証コードを再送する」を押す。
   - 送信から60秒間は「◯秒後に再送できます」と表示され、押せない。
   - 新しいコードが発行され、古いコードは使えなくなる。
   - API は同じIP・同じ操作ごとに送信を60秒に5回までに制限し、サーバーの再起動後も回数を保持する。
   - メールアドレス単位の1時間5回制限は設けない。上限に達すると429を返し、最後に受け付けた操作から60秒後に再開できる。
4. 最新のコードを5分以内に入力し、「確認してはじめる」を押す。
   - 確認が完了してホームへ進む。同じコードは再利用できない。
5. アカウント画面からログアウトし、メールアドレスとパスワードでログインする。
   - 確認済みの場合はコードの再入力を求めない。
   - 同一IPでのログイン試行は60秒に10回まで。
6. 未確認のアカウントでログインする。
   - パスワードが正しい場合はメール確認画面に進み、再送して再開できる。
   - 以前発行された未確認のセッションが残っていてもホームの機能を利用できない。
7. メール確認画面で「ログイン画面に戻る」を押す。
   - 未確認のセッションを消してログイン画面へ移る。
8. テストの送信処理を失敗させる。
   - 送信成功として扱わず、未確認のままで再送から再開できる。

## データの持ち方

- `user.emailVerified` が確認済みの状態を表す。
- `verification` はコードのハッシュ、有効期限、試行回数を持つ。
  - 有効期限は5分、誤入力は5回まで。コードを消費する処理は原子的に行う。
- `rate_limit` は Better Auth 標準の保存先として、ID、IPと操作パスによるキー、回数、最終操作時刻を持つ。
  - D1 に保存し、Worker の再起動後も制限を維持する。古い行の削除も Better Auth に任せる。
- 確認が済むとログインした状態になる（`autoSignInAfterVerification`）。画面は `apps/web/src/routes/app/_guest/verify-email.tsx`。
- これは登録メールアドレスの確認であり、通常のログインに毎回二要素認証を要求する仕様ではない。
